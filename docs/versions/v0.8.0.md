# v0.8.0 — Chat Integration

> 当前状态：Stage 1、Stage 2、Stage 3 均已完成真实 WordPress 验收并封板；下一步进入 v0.8.0 Final Review

## 一、版本目标

v0.8.0 不重新开发 AI Engine，而是把 v0.5.0～v0.7.0 已验证的能力接到真实匿名访客入口：

```text
Visitor
  ↓
Public Chat Boundary
  ↓
Conversation / Visitor / Site Context
  ↓
WPAIC_Grounded_Answer_Service
  ↓
Local Retrieval → Grounding Gate → Usage Guard → AI Provider
```

核心原则：**Chat 只是入口，不拥有 AI 逻辑。**

## 二、参考源码定位

- `simple-live-chat`：Stage 2 前端 UI 基线。
- `wp-live-chat-inquiry`：Visitor / Conversation / REST / State 架构参考，不整体合并。
- `wp-ai-chat-lab`：唯一正式插件主体与 AI 核心。

## 三、Stage 1 已实现

- `POST /wp-json/wpaic/v1/chat`
- Conversation UUID：请求未提供时服务器生成并返回
- Visitor UUID：服务器生成，使用 `wpaic_visitor` HttpOnly Cookie 持久化
- Site Context：服务器生成，Public Request 无法覆盖
- Public Contract：`answer / clarify / no_answer / blocked / error`
- Public Response 不暴露 Retrieval Score、Provider、Model、Token、Usage Hash、内部 Reason Code
- Admin `Chat Boundary` Playground 直接调用真实 Public REST
- Usage Counter 必须为 InnoDB；不满足 transaction / row-lock prerequisite 时 fail closed
- Transaction-critical wpdb failure 明确 rollback + `usage_guard_unavailable`

## 四、数据库

- Plugin Version：`0.8.0`
- DB Version：`1.1`
- 新增表：0
- 仍只有 Knowledge Store + Usage Counter

## 五、Public Request

```json
{
  "question": "What are the dimensions of CWC-610?",
  "conversation_id": "optional UUID v4"
}
```

Public Client 不能控制 Visitor / Site、Provider / Model、Usage Limit、Grounding Threshold、Candidate Limit 或 Top K。

## 九、Stage 2 — Simple Chat UI Integration

Stage 2 将 `simple-live-chat` 的视觉结构迁入插件，但删除原 Demo `replies{}` Answer Engine。前端只负责 UI / Session State，所有问题统一请求 Stage 1 已验证的 Public REST。

已实现：

- 新增 `public/` 前端层：Widget Renderer + 独立 CSS + Vanilla JS + View。
- 前台 Widget 默认关闭，由永久 `Chat UI Lab` 页面显式启用。
- 保留 simple-live-chat 的 Launcher / Panel / Header / Quick Questions / Message Bubble / Mobile Layout。
- Conversation ID 保存到 `sessionStorage`；同一标签页刷新后恢复当前 Conversation 与本地消息气泡。
- Visitor 仍只由服务器 HttpOnly Cookie 管理；前端不读、不写 Visitor ID。
- Quick Questions 与普通输入都调用真实 `/wp-json/wpaic/v1/chat`。
- 请求期间显示 Typing，并禁用输入 / Quick Question / Send，避免同一 UI 重复提交。

- `blocked` 后当前 Conversation 停止继续发送；Header 的“新会话”只重置 Conversation + 本标签页消息，不重置 Visitor。
- 前端不显示 Provider / Model / Token / Score / Internal Reason Code。
- 新增永久 `Chat UI Lab` 页面，保存 Enable 开关与 Stage 2 回归路线。

## 十一、Stage 3 — Public Hardening & Remaining Operational Boundaries

Stage 3 不再重复 Stage 2 已通过的断网、慢网、重复发送、刷新连续性和手机端，而只处理尚未验证的公共边界。

### Round 1 — Request Guard + Visitor / Site Operational Limits

本轮新增：

- `WPAIC_Public_Request_Guard`：位于 Public REST 与 Grounded Answer 之间，专门限制公开请求频率。
- Request Guard 与 Usage Guard 完全分离：前者保护 REST / Retrieval 资源，后者继续精确保护 Provider Call。
- 固定 60 秒窗口，使用短期 WordPress Transient；只保存 Visitor / IP 哈希，不保存原始 IP。
- 默认启用 Visitor 20 次/分钟；IP Limit 默认 `0`（关闭），避免 Cloudflare / 反向代理环境误把共享出口当成真实访客 IP。
- HTTP 429 使用现有 Public `error` Contract，前端不会永久锁死 Conversation；返回 `Retry-After`。
- 新增永久 `Public Hardening` Lab：可以查看 Request Guard、Visitor Daily、Site Daily 状态，保存 Rate 设置，并安全重置当前 Visitor / Site / Request Rate 测试状态。
- 新增数据库表：0；DB Version 继续保持 `1.1`。
- Request Rate 是 best-effort 应用层保护，不作为账单或精确 Provider Quota；高流量生产防护仍建议放在 Cloudflare / WAF。

Round 1 真实验收已完成：

1. Visitor Daily Limit：`Conversation=10 / Visitor=2 / Site=20`，前两次 Strong 正常 answer，第 3 次准确 Visitor BLOCK；计数保持 Visitor `2/2`、Site `2/20`。✅
2. Site Daily Limit：`Conversation=10 / Visitor=10 / Site=2`，前两次 Strong 正常 answer，第 3 次准确 Site BLOCK；计数保持 Visitor `2/10`、Site `2/2`。✅
3. Request Rate Limit：Visitor/Minute 临时设为 3，前三次 `dimension` 正常 clarify，第 4 次 HTTP 429 / `error`。✅
4. 60 秒窗口结束后再次发送 `dimension` 自动恢复 clarify，无需 Reset。✅
5. Request Rate 测试期间 Provider Usage 不增加，证明 Public Request Guard 与 Usage Guard 相互隔离。✅

**Round 1 结论：Validation Passed。**

### Round 2 — Provider Failure Boundary

Round 2 不通过改坏 API Key、修改 DeepSeek URL 或等待真实故障来测试。新增永久 `WPAIC_Provider_Failure_Lab`：

- 管理员可以为当前 Visitor 武装一次 `transport_timeout`。
- 测试状态只保存当前 Visitor 的哈希身份，180 秒自动过期，一次性消费。
- Chat Controller 只在当前 Public Request 周期临时挂载 Failure Injector。
- AI Manager 增加中性的 `wpaic_ai_manager_pre_chat_result` 扩展点；未武装时不改变正常 Provider 路径。
- Failure 只有在 Grounding = Strong、Usage Guard 已 Reserve、请求真正进入 AI Manager 时才会触发。
- Weak / Medium / None / Usage BLOCK 不调用 AI Manager，因此不会消费 Failure Arm。
- 触发后 Grounded Answer 返回 Provider WP_Error，Public Chat 继续走既有 fail-safe：HTTP 503 / `error`，Widget 显示临时不可用并恢复可发送状态。
- Provider Call Reservation 已经发生，因此失败尝试保守计入 Provider Call；没有可信 Provider Usage 响应，所以 Token 不增加。
- Failure 为 one-shot，下一次不重新武装的 Strong 请求应恢复真实 Provider answer。
- Public Hardening Lab 新增 Failure `Armed / Idle` 状态、Arm / Clear 控件，以及 Visitor / Site Token 快照。

Round 2 真实验收已完成：

1. 设置较高 Usage / Request Rate、重置当前 Visitor / Site / Request Rate，并开启新 Conversation。✅
2. 武装下一次 Provider Timeout 后先发 `dimension`：正常 `clarify`；Failure 仍保持 Armed，Visitor / Site Usage 与 Token 均不增加。✅
3. 在 Failure 有效期内立即发送 `CWC-610 dimension`：Strong 通过 Grounding 与 Usage Reservation 后命中模拟 Transport Timeout；正式 Widget 显示临时不可用。✅
4. Failure 命中后自动回到 Idle；Visitor / Site Calls 各 +1，但失败请求没有可信 Provider Usage，因此 Tokens 仍为 0。✅
5. 不重新武装，再发同一 Strong：真实 Provider 恢复正常 `answer`；Calls 再 +1，Token 只在成功响应后增加（本次验证为 580）。✅
6. 180 秒 TTL 行为得到额外确认：人工测试若超过有效期，Failure 自动过期，后续请求安全走正常 Provider，不修改 API Key / Endpoint / 正式配置。✅

**Round 2 结论：Validation Passed。**
