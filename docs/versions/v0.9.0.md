# v0.9.0 — Lead Capture & Inquiry Management

> Status: **Planning / Architecture Baseline**  
> Implementation: **Not started**  
> Current stable release remains: **v0.8.0 — Chat Integration**

---

## 1. 版本定位

v0.9.0 不把 WP AI Chat Lab 扩展成完整 CRM，也不进入实时人工客服。

本版本只解决两个业务问题：

1. **什么时候应该自然地邀请访客提交询盘？**
2. **询盘提交后，WordPress 后台如何保存、查看和处理？**

整体路径：

```text
Knowledge
↓
Retrieval
↓
Grounding
↓
Usage Guard
↓
Chat
↓
Lead Trigger Policy
↓
Inquiry Form
↓
Inquiry Service / Repository
↓
wp_wpaic_inquiries
↓
后台 Inquiry Management
```

核心原则：

> **先帮助，再转化。**  
> AI 的首要任务仍然是可靠回答问题；只有在用户主动表达需求、AI 无法继续帮助或业务边界自然出现时，系统才提供询盘入口。

---

## 2. 架构边界

Chat 与 Inquiry 必须保持独立：

```text
Chat Response
     ↓
Lead Trigger Policy
     ↓
Should Offer Lead?
 ┌──────┴──────┐
 No            Yes
 ↓              ↓
继续聊天        CTA
                 ↓
             用户主动点击
                 ↓
           Inline Inquiry Form
                 ↓
           Inquiry Controller
                 ↓
            Inquiry Service
                 ↓
          Inquiry Repository
                 ↓
         wp_wpaic_inquiries
```

Lead Trigger Policy **只决定是否显示邀请**，不能直接保存询盘，也不能强制弹出表单。

---

## 3. Lead Trigger Policy

第一版采用 **Deterministic Policy（确定性规则）**，不额外调用 AI 判断购买意图。

### 3.1 Trigger Types

第一版只保留四类：

```text
manual
commercial_intent
no_answer
usage_blocked
```

### 3.2 manual

用户主动点击：

- Request a Quote
- Contact Sales
- Leave a Message

这是最高确定性的询盘入口。

### 3.3 commercial_intent

当问题包含明确商业需求关键词时，Chat 仍优先正常回答，然后在回答下方显示 CTA。

示例：

```text
Can I get a quote for 500 sqm CWC-610?
↓
正常 answer
+
Request a Quote CTA
```

### 3.4 no_answer

当现有知识不足以可靠回答时：

```text
no_answer
↓
提示当前知识不足
↓
Leave a Message CTA
```

这是“AI 解决不了 → 留给团队后续处理”，不是实时 Human Handoff。

### 3.5 usage_blocked

- `conversation_limit_reached`：主要 CTA 仍是 Start New Conversation，询盘 CTA 只作为次级入口。
- `visitor_daily_limit_reached`：可以明显提供 Leave Your Requirement。
- `site_daily_limit_reached`：AI 暂时不可继续时，询盘是自然 fallback。

### 3.6 不自动触发 Lead 的情况

以下状态默认不显示自动 Lead CTA：

```text
clarify
Weak
Medium
ordinary answer without commercial intent
HTTP 429 request rate limit
HTTP 503 provider error
network error
invalid conversation
```

系统故障、滥用保护或问题不够明确时，不应该借机强制收集个人信息。

## 4. Commercial Intent Keywords — 后台完全可配置

这是 v0.9.0 的固定产品原则：

> **商业需求关键词不能写死在代码中。**

插件只提供一组默认值，管理员可以在后台完整控制。

### 4.1 后台能力

第一版设置页至少支持：

- 查看默认关键词；
- 添加关键词；
- 删除关键词；
- 修改关键词；
- 一行一个关键词 / 短语；
- 保存后立即生效；
- 恢复默认关键词；
- 允许保存空列表。

**空列表的语义：关闭 commercial_intent 关键词触发。**

插件不能在管理员清空后自动重新写入默认值；只有管理员主动点击“恢复默认关键词”时才恢复。

### 4.2 默认关键词（初始建议）

```text
quote
quotation
price
pricing
sample
order
MOQ
minimum order
bulk
custom
customized
OEM
ODM
distributor
dealer
shipping
delivery
contact sales
```

默认值只是开箱即用起点，不代表固定规则。

### 4.3 多语言

设置应允许任意 Unicode 文本，因此管理员可以自行增加：

```text
报价
价格
样品
起订量
定制
代理
经销商
交期
联系我们
```

或其它语言关键词。

### 4.4 存储建议

使用 WordPress Option 保存标准化后的关键词数组，例如：

```text
wpaic_lead_commercial_keywords
```

不为关键词单独创建数据库表。

### 4.5 匹配原则

第一版保持简单、可解释：

- Trim + 去除空项；
- 去重；
- Latin 文本大小写不敏感；
- 支持多词短语；
- 不调用 AI；
- 每一次匹配结果都应能从后台配置中解释。

后续若真实数据表明误判明显，再升级规则，不提前引入复杂 NLP / Lead Scoring。

## 5. Trigger Priority

当同一请求同时满足多个触发条件时，第一版建议固定优先级：

```text
manual
↓
commercial_intent
↓
no_answer
↓
usage_blocked
```

示例：问题本身明确要求报价，即使最终知识不足，也优先使用 `commercial_intent` 的 Request a Quote CTA，而不是泛化的 Leave a Message。

## 6. Inquiry Form

第一版使用 Chat 内联表单，不再打开第二层 Modal。

### 必填

```text
Name
Email
Message
```

### 选填

```text
Company
Phone / WhatsApp
```

暂不增加：

```text
Country
Quantity
Budget
Product selector
Job title
Address
```

真实使用后再根据提交数据决定是否增加。

### 6.1 Message 预填

CTA 打开表单时，可以根据当前问题预填 Message，例如：

```text
I'm interested in CWC-610.
My requirement is approximately 500 sqm.
```

用户可以继续修改。

### 6.2 提交成功

不跳转页面：

```text
Thank you. Your request has been submitted successfully.
Our team will get back to you soon.

[ Continue Chatting ]
```

## 7. Inquiry Database

Inquiry 属于运营数据，不属于网站内容，因此第一版使用独立自定义表，而不是 CPT。

计划表名：

```text
wp_wpaic_inquiries
```

### 7.1 建议字段

```text
id
created_at
updated_at
status

name
email
phone
company
message

trigger_type
trigger_reason
conversation_id
source_url
last_question
visitor_hash
```

建议索引：

- `status`
- `created_at`
- `email`（如实际查询需要）

### 7.2 明确不保存

v0.9.0 第一版不自动保存：

```text
完整 Conversation
完整 Chat Transcript
Prompt
AI Answer
原始 Visitor UUID
原始 IP
Provider Token Detail
```

遵循最少采集原则。

### 7.3 DB Version

规划阶段仍保持当前：

```text
Plugin Version = 0.8.0
DB Version = 1.1
```

真正进入 v0.9.0 Stage 1、创建 `wp_wpaic_inquiries` 时，再正式评估并升级 DB Version（预计进入下一 schema version）。

## 10. Inquiry Service Boundary

禁止在 REST Controller 中直接散落 `$wpdb->insert()`。

正式结构：

```text
Public Inquiry Controller
        ↓
Inquiry Service
        ↓
Inquiry Repository
        ↓
wp_wpaic_inquiries
```

这样后续后台列表、状态修改、Spam、删除、导出等都复用 Repository。

---

## 11. Spam / Abuse Foundation

第一版只做最小防护：

### Honeypot

隐藏字段，例如：

```text
website
```

正常用户为空；非空直接拒绝。

### Submission Rate Limit

使用短期 Transient，例如：

```text
同一 Visitor：5 submissions / hour
```

不混入 AI Usage Counter。

### Server Validation

至少包括：

```text
Name length
Email format
Message length
Phone length
Company length
Trigger allowlist
Conversation UUID
```

### 暂不加入 Turnstile

真实上线出现明显垃圾询盘后，再评估 Cloudflare Turnstile。

---

## 12. Database Failure Policy

Inquiry 写入与普通 Chat 不同：不能出现“UI 显示提交成功，但数据库实际失败”。

必须：

```text
Repository Insert
↓
明确确认成功
↓
才返回 Public Success
```

数据库写入失败：

```text
HTTP 500
public error
```

严格 fail closed。

## 16. Lab / Playground Policy

延续项目既有规则：

> **所有用于教学、诊断、验证架构的 Lab / Playground / Validation 页面长期保留。**

v0.9.0 新增的 Lead Trigger / Inquiry Playground 在版本完成后也不删除，而是作为后续规则调整、数据库诊断和版本回归工具。

## 17. 设计结论

v0.9.0 的核心不是“让 Chat 多一个表单”，而是建立一个清晰的业务边界：

```text
先帮助
↓
建立信任
↓
识别明确商业需求或帮助边界
↓
自然邀请询盘
↓
用户主动提交
↓
保存最少必要信息
↓
后台跟进
```

其中 `commercial_intent` 必须始终遵循：

> **默认值只是起点；最终规则由网站管理员在后台完全控制。**
