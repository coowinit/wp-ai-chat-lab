# v0.7.0 — Usage Guard

> v0.6.0 已经解决“只有本地 Evidence 足够可靠时，才允许 AI Provider 生成 Grounded Answer”。v0.7.0 开始解决下一层问题：**即使问题可以回答，也不能让公共网站无限调用 AI。**

**版本：v0.7.0**  
**阶段：Usage Guard**  
**状态：Stage 1 Validation Passed / Ready for Stage 2 Provider Boundary Integration**  
**前置版本：v0.6.0 — Grounded AI（Stable Release）**

---

# 一、版本背景

截至 v0.6.0，项目已经形成：

```text
WordPress Source
        ↓
Unified Knowledge Source
        ↓
Knowledge Store
        ↓
Lifecycle
        ↓
Local Retrieval
        ↓
Grounding Gate
        ↓
Evidence Pack
        ↓
Grounded Prompt
        ↓
AI Manager
        ↓
DeepSeek
        ↓
Grounded Answer + Source Trace + Usage
```

真实网站已经验证：

```text
CWC-610 dimension
→ Strong
→ allow_answer
→ AI Called = Yes
→ Grounded Answer

CWC-610 warranty
→ Medium
→ clarify
→ AI Called = No

 dimension
→ Weak
→ clarify
→ AI Called = No

ZXQ-99999-NOMATCH
→ None
→ no_answer
→ AI Called = No
```

v0.6.0 已经证明：

> **有可靠 Evidence 才能调用 AI。**

但如果一个真实公共网站上线以后，访客可以不断提出“有可靠 Evidence 的问题”，仍然可能产生：

```text
无限 Provider Call
无限 Token
异常机器人请求
重复查询
不可控 API 成本
```

因此 v0.7.0 的任务不是继续提高回答能力，而是建立：

# AI Provider Boundary 前的 Usage Guard。

---

# 二、这一版最重要的原则：Grounded ≠ Unlimited

v0.6.0 的硬规则是：

```text
No Reliable Knowledge
→ No AI Call
```

v0.7.0 再增加一层：

```text
Reliable Knowledge
≠
Unlimited AI Call
```

完整应用层顺序应该逐步变成：

```text
Question
↓
Local Retrieval
↓
Grounding Gate
↓
Evidence / Prompt Preparation
↓
Usage Guard
↓
只有 Usage Guard 允许
↓
AI Provider
```

因此：

# Application Gate > Prompt > Provider

Prompt 仍然不是成本控制边界。

---

# 三、v0.7.0 仍然不是完整 Chat

虽然本版本会出现：

```text
Conversation Limit
Visitor Daily Limit
Site Daily Limit
```

但 v0.7.0 **不建立完整 Conversation 系统**。

本版本不做：

```text
Conversation Table
Message Table
Front-end Chat Widget
Multi-turn Context
Lead Capture
Human Handoff
```

Usage Guard 只接受调用方传入的稳定 Scope Key：

```text
conversation_key
visitor_key
site_key
```

未来 v0.8.0 Chat Integration 再把真实 Chat Conversation / Visitor ID 接入这些接口。

也就是说：

> **Usage Guard 与 Chat 解耦。**

---

# 四、第一版 Usage Guard 的三个范围

v0.7.0 第一版只做三个最有价值的限制：

```text
Conversation AI Call Limit
Visitor Daily AI Call Limit
Site Daily AI Call Limit
```

默认设计基线：

```text
Conversation: 10 Provider Calls / conversation lifetime
Visitor:      20 Provider Calls / WordPress local day
Site:        200 Provider Calls / WordPress local day
```

这些值是实验默认值，不是永久业务规则。

后台应允许管理员配置。

建议语义：

```text
0 = 不启用该 Scope 限制
正整数 = Provider Call 上限
```

---

# 五、为什么限制的是 Provider Call，而不是用户消息数

Usage Guard 不应该统计：

```text
用户发送了多少条 Message
Retrieval 跑了多少次
Grounding Gate 跑了多少次
clarify 返回了多少次
no_answer 返回了多少次
```

真正需要保护的是：

```text
Provider Boundary
```

因此第一版核心指标定义为：

# Provider Call Count

例如：

```text
dimension
→ Weak
→ clarify
→ Provider Call = 0
→ Usage Counter 不增加
```

而：

```text
CWC-610 dimension
→ Strong
→ allow_answer
→ Provider Call = 1
→ Conversation / Visitor / Site 三个 Scope 同时 +1
```

这使 Usage Guard 与真实成本边界一致。

---

# 六、失败调用是否计数

第一版设计建议：

> **只要真正越过 Provider Boundary 并尝试调用外部 AI，就计入 Provider Call。**

原因：

- Provider timeout 也可能产生外部资源消耗；
- 重复失败请求本身也可能成为滥用方式；
- 不应该允许攻击者通过失败请求绕过限制。

因此：

```text
Usage Reservation
↓
Provider Call Attempt
↓
无论最终成功还是 Provider Error
Provider Call Count 都已占用
```

如果 Provider 成功返回 Usage，则再记录：

```text
prompt_tokens
completion_tokens
total_tokens
```

Token 在 v0.7.0 **只记录，不作为限制条件**。

Monthly Token / Cost Budget 留给未来 Cost Guard。

---

# 七、Usage Guard 应放在什么位置

为了避免无意义计数，建议 Provider 调用前的最终顺序：

```text
Question
↓
Local Retrieval
↓
Grounding Gate
↓
allow_answer only
↓
Evidence Pack
↓
Grounded Prompt
↓
Provider Configuration Check
↓
Usage Guard Reserve
↓
AI Manager
↓
Provider
↓
Record Token Usage
```

为什么不是一开始就计数？

因为下面这些本地失败不应该消耗 AI Call Quota：

```text
No Evidence
Weak / Medium Gate
Evidence Build Failure
Prompt Build Failure
API Key Missing
Provider 未配置
```

只有已经准备真正越过 Provider Boundary 时，才 Reserve Provider Call。

# 八、Usage Context Contract

v0.7.0 建议建立统一 Usage Context：

```php
[
    'conversation_key' => '...',
    'visitor_key'      => '...',
    'site_key'         => 'site',
]
```

第一版不要求这些 Key 来自数据库对象。

它们只需要：

```text
稳定
不可空（对应 Scope 已启用时）
对同一对象保持一致
```

未来 v0.8.0：

```text
conversation_key
→ 真实 Conversation ID / UUID

visitor_key
→ 前台 first-party visitor UUID
```

---

# 九、隐私：不使用 IP 作为 Visitor ID

第一版明确：

```text
Visitor Limit
≠
IP Limit
```

不建议直接把 IP 地址作为 Visitor Key：

- NAT / 公司网络会共享 IP；
- 移动网络 IP 会变化；
- IPv6 / Proxy / CDN 情况复杂；
- IP 属于更敏感的访问数据。

未来 v0.8.0 Chat 建议生成 first-party 随机 Visitor UUID。

服务端持久化前：

```text
Raw Visitor Key
↓
HMAC / SHA-256 Hash
↓
usage_counter.scope_key_hash
```

数据库不需要保存原始 Visitor ID。

Conversation Key 同样建议只保存 Hash。

---

# 十、缺少 Usage Context 时的原则：Fail Closed

如果管理员启用了：

```text
Conversation Limit > 0
```

但调用方没有提供：

```text
conversation_key
```

则不能静默跳过该限制。

应返回：

```text
decision: block
reason_code: missing_usage_context
```

同理 Visitor Scope。

原则：

> **一个已经启用的 Guard 不能因为 Context 缺失而自动失效。**

后台 Playground 可以提供明确的测试 Key，例如：

```text
lab-conversation-1
lab-visitor-1
```

# 十一、第一版数据库设计

v0.7.0 建议新增第二张自定义表：

```text
{$wpdb->prefix}wpaic_usage_counter
```

Knowledge Store 继续保持原表，不混在一起。

建议字段：

```text
id
scope_type
scope_key_hash
period_key
provider_calls
prompt_tokens
completion_tokens
total_tokens
last_called_at
created_at
updated_at
```

唯一键：

```text
(scope_type, scope_key_hash, period_key)
```

Scope Type：

```text
conversation
visitor
site
```

Period Key：

```text
conversation → lifetime
visitor      → YYYY-MM-DD
site         → YYYY-MM-DD
```

Visitor / Site 日期使用：

```text
WordPress Site Timezone
```

而不是服务器 UTC 日期。

# 十二、为什么不用 transient 作为核心 Guard

Transient 很适合缓存，但不适合作为第一版核心 Usage Enforcement Source：

- 可能提前失效；
- 可能被 Object Cache 后端影响；
- 不方便同时保存 Token Usage；
- 不容易形成可诊断的跨 Scope 状态；
- 未来 Chat / Human Handoff 需要更稳定的数据基础。

因此：

```text
Usage Counter Table
= Source of Truth for Usage Guard
```

缓存以后有真实性能需求再加。

# 十五、Reason Code

第一版建议固定：

```text
within_limits
conversation_limit_reached
visitor_daily_limit_reached
site_daily_limit_reached
missing_usage_context
usage_guard_unavailable
```

不要让前台根据中文文案判断逻辑。

未来可根据 reason code 显示不同体验：

```text
conversation_limit_reached
→ 建议开启新会话 / 联系人工

visitor_daily_limit_reached
→ 今日 AI 次数已用完，可继续留言

site_daily_limit_reached
→ AI 暂时不可用，可继续使用人工渠道
```

---

# 十六、多 Scope 同时检查

每一次真正 Provider Call 都同时受三个 Scope 保护：

```text
Conversation
AND
Visitor
AND
Site
```

只要任何一个 Scope 达到上限：

```text
AI Call = Block
```

不是：

```text
三个限制全部超限才 Block
```

因此：

```text
Allow AI
=
Conversation OK
AND Visitor OK
AND Site OK
```

---

# 十七、阻断优先级

如果多个 Scope 同时达到上限，第一版建议稳定返回：

```text
Conversation
↓
Visitor
↓
Site
```

原因是优先给出最具体、最容易让用户理解和恢复的限制。

但实际保护效果不依赖优先级：任何一个超限都会 Block。

---

# 十八、并发与原子 Reserve

Usage Guard 是应用边界，不应该简单采用：

```text
SELECT 当前计数
↓
PHP 判断
↓
UPDATE +1
```

因为两个并发请求可能同时读取同一个旧值。

第一版实现目标应是：

```text
reserve_provider_call()
```

在同一个短事务中：

```text
确保当前 Scope Row 存在
↓
锁定 Conversation / Visitor / Site 当前 Row
↓
检查三个 Scope
↓
任意超限 → rollback / block
↓
全部允许 → 三个 Scope provider_calls +1
↓
commit
```

然后才真正调用 Provider。

这样 Provider Boundary 前的 Call Quota 尽量保持一致。

如果当前数据库无法完成 Usage Guard 持久化：

```text
Fail Closed
→ usage_guard_unavailable
→ AI Called = No
```

而不是跳过 Guard。

---

# 十九、Token Usage 的记录方式

Reserve 时只增加：

```text
provider_calls +1
```

Provider 成功返回以后，再根据真实 Provider Usage 增加：

```text
prompt_tokens
completion_tokens
total_tokens
```

因此一次 Call 的生命周期：

```text
Reserve
↓
Provider Call
↓
Provider Response
↓
Commit Token Usage
```

Provider Error：

```text
provider_calls 已占用
Token Usage 没有可靠值时保持 0
```

第一版不尝试猜 Token。

---

# 二十、v0.7.0 不做 Cost Guard

虽然表中记录 Token，但第一版不根据 Token Block。

不做：

```text
Monthly Token Limit
Monthly Cost Limit
USD Budget
RMB Budget
Provider Price Calculation
```

原因：

- Provider 定价可能变化；
- 不同 Model 价格不同；
- 成本换算会把 Usage Guard 与 Provider Billing 过度耦合。

当前只记录 Usage，为未来 Cost Guard 留数据基础。

# 二十三、Blocked 时的 Deterministic Reply

Usage Guard Block 后不应调用 AI 生成“超限提示”。

直接应用层返回固定结果。

例如 Conversation Limit：

```text
当前会话的 AI 回答次数已达到限制。你可以稍后继续，或留下联系方式转人工处理。
```

Visitor Limit：

```text
今天的 AI 使用次数已达到限制。你仍可以继续浏览网站或提交询盘。
```

Site Limit：

```text
AI 服务暂时达到今日使用上限。你可以继续使用网站的其他功能或联系人工。
```

这些提示：

```text
AI Called = No
Token Usage = 0
```

---

# 二十四、Usage Guard 与 Grounding Gate 的关系

两个 Gate 解决不同问题：

## Grounding Gate

问：

> **有没有足够可靠的知识证据？**

## Usage Guard

问：

> **即使可以回答，这次请求还有没有 AI 调用额度？**

因此：

```text
Grounding Gate
≠
Usage Guard
```

两者不能合成一个大类。

这样未来可以分别测试、修改和复用。

---

# 二十五、为什么 Grounding 先于 Usage

例如用户问：

```text
how to learn python
```

如果本地业务知识没有匹配：

```text
Grounding Gate
→ no_answer
→ Provider Call = 0
```

这个问题根本不应该消耗：

```text
Conversation AI Limit
Visitor Daily Limit
Site Daily Limit
```

因此：

```text
Grounding First
Usage Second
```

可以避免无关问题消耗合法用户的 AI 配额。

# 二十六、v0.7.0 的成功标准

这一版本成功，不是因为后台多了几个数字。

而是必须证明：

```text
Strong + Grounded
+ Usage Available
→ AI Called = Yes
→ Counter +1

Strong + Grounded
+ Conversation Limit Reached
→ AI Called = No
→ Token Usage = 0

Strong + Grounded
+ Visitor Limit Reached
→ AI Called = No
→ Token Usage = 0

Strong + Grounded
+ Site Limit Reached
→ AI Called = No
→ Token Usage = 0

Weak / Medium / None
→ Grounding 先阻断
→ Usage Counter 不增加
```

这才是真正的 Usage Guard。

# 二十八、Stage 1 — Usage Store & Policy Foundation

第一阶段只建立 Usage 基础设施，不马上接真实 Provider Boundary。

实现：

```text
DB Version 1.1
wpaic_usage_counter
WPAIC_Usage_Counter_Repository
WPAIC_Usage_Context
WPAIC_Usage_Guard
Usage Settings
Usage Diagnostics
```

目标：

- 表自动升级创建；
- Scope Hash 稳定；
- Conversation / Visitor / Site 当前计数可读取；
- Guard 能根据模拟计数输出 allow / block；
- 缺 Context 时 fail closed；
- 暂不修改 Grounded Answer Provider Call。

↓

↓
Prompt
↓
Provider Config Check
↓

↓

重点验证：

- quota block → Provider 完全不调用；
- block 路径 Token = 0；

# 三十三、与 Cloudflare / Security Plugin 的关系

Usage Guard 处理：

```text

```

```text

IP / Bot

Rate Limiting

```

两者职责不同。

不应该把 Usage Guard 发展成一个简化版 WAF。

# 最终原则

v0.7.0 的目标不是：

> **让 AI 少回答一点。**

而是：

> **让每一次真正越过 Provider Boundary 的调用，都同时满足“有可靠证据”和“有可用额度”两个条件。**

因此这一版的核心可以压缩成一句话：

# Grounded First. Usage Guard Second. Provider Last.

# Stage 2 — Provider Boundary Integration

## Validation Passed

Stage 2 已把 Stage 1 验证通过的 Usage Guard 接入真实 Grounded Answer Provider Boundary。

当前顺序：

```text
Question
→ Local Retrieval
→ Grounding Gate
→ Evidence Pack
→ Grounded Prompt
→ Usage Guard Reserve
→ WPAIC_AI_Manager
→ Provider
→ Token Accounting
```

核心实现：

- `WPAIC_Grounded_Answer_Service` 现在依赖 `WPAIC_Usage_Guard`。
- `allow_answer` 构建 Evidence / Prompt 后，在 Provider Call 前执行 `reserve()`。
- `clarify / no_answer` 在 Grounding Gate 后直接返回，Usage Guard 保持 `skipped`。
- Usage BLOCK 返回确定性 `usage_block` 结果，不调用 Provider。
- Provider 未配置时不会提前消耗 Usage Reservation。
- Reservation 成功后才允许设置 `AI Called = Yes` 并调用 `WPAIC_AI_Manager`。
- Provider Call Attempt 一旦发生，Provider Call Counter 已经保留；Provider Error 不回滚 Call Counter。
- Provider 成功响应后使用可信 `usage` 数据累计 Prompt / Completion / Total Tokens。
- Token Accounting 更新 Conversation / Visitor / Site 三个已启用 Scope。
- Grounded AI Playground 新增 Usage Context：Conversation Key / Visitor Key / Site Key。
- Grounded Answer 结果新增 Usage Guard Panel，显示 Decision / Reason Code / Scope Calls / Remaining / Token Counters。
- 独立 Usage Guard Playground 保留，用于继续验证 Guard 本身；真实 Grounded AI 页面使用同一套 Reservation。
