# v0.3.0 — Knowledge Source Foundation

> WP AI Chat Lab 的第二个正式功能开发阶段。  
> 本版本负责建立 **WordPress Content → Clean Knowledge Source** 的基础链路。

**版本：v0.3.0**  
**阶段：Knowledge Source Foundation**  
**状态：Design Ready**  
**前置版本：v0.2.0 — AI Provider Foundation**

---

# 一、版本背景

v0.1.0 完成：

- 项目定位；
- Tidio / Lyro 对照研究；
- Knowledge / Retrieval / Grounding / Human Handoff 总体架构；
- 长期 Roadmap。

v0.2.0 完成：

- AI Provider Interface 思路；
- AI Manager；
- DeepSeek Provider；
- API Key；
- Model；
- Connection Test；
- Minimal AI Test；
- Unified AI Response；
- Error Model；
- 实际 WordPress 环境测试。

v0.3.0 开始正式进入：

# WordPress Knowledge

但本版本暂时不解决：

```text
Knowledge
→ Chunk
→ Retrieval
→ AI Answer
```

只解决：

```text
WordPress Content
→ Clean Knowledge Source
```

---

# 二、设计评审结论

在正式开发前，对 Knowledge Source 架构进行了多模型独立评审。

综合评审结果后，确认以下主方向：

# Generic + Structured + Manual Knowledge

但 v0.3.0 进一步收紧范围：

```text
v0.3.0
→ Generic Knowledge Source Foundation

v0.3.1
→ WEM Structured Source Validation
```

也就是说：

> v0.3.0 不提前构建完整 Adapter Framework。

先用一个真实可工作的 Generic Extractor 跑通完整知识来源管道。

等 v0.3.1 加入第二个真实实现 WEM Extractor 后，再根据真实需求决定是否正式抽象 Interface / Registry。

---

# 三、核心原则

v0.3.0 必须继续遵守以下原则。

## 1. Single Source of Truth

业务内容继续保存在原来的 WordPress 内容类型中。

例如：

```text
Product
Solution
FAQ
Page
Post
```

AI 插件不重新建立：

```text
AI Product
AI Solution
AI FAQ
```

避免双份数据和同步问题。

---

## 2. Generic First

普通 WordPress 网站即使没有 WEM、WooCommerce、ACF，也应该可以使用基础 Knowledge Source。

因此首先实现：

```text
Generic Extractor
```

---

## 3. Structured Data 属于 Progressive Enhancement

未来：

```text
WEM
WooCommerce
ACF
Meta Box
```

可以提供更高质量的结构化知识。

但这些属于后续 Structured Extractor。

Core 不绑定任何业务插件。

---

## 4. 默认不读取 Post Meta

Generic Extractor：

```text
post_meta = none
```

不自动读取：

```text
Elementor
SEO
Theme
Cache
Plugin Internal Meta
```

未来结构化 Extractor 必须采用：

# Explicit Allowlist

---

## 5. 默认全部关闭

首次进入 Knowledge Sources：

```text
Post        ☐
Page        ☐
Product     ☐
Solution    ☐
FAQ         ☐
```

管理员主动选择：

> 哪些 WordPress 内容允许成为 AI Knowledge。

插件不自动授权。

---

## 6. 先解决 Source，再解决 Retrieval

v0.3.0 不做：

```text
Chunk
Embedding
Vector
Search
Retrieval
RAG
Grounding
AI Answer
```

一次只验证一个层。

# 五、为什么增加 Content Normalizer

WordPress 的：

```text
post_content
```

并不天然等于 AI 可以直接使用的干净文本。

真实网站中可能包含：

```text
Gutenberg Block Comments
Shortcodes
HTML
<script>
<style>
HTML Comments
Page Builder Markup
Repeated Whitespace
Entities
```

因此必须明确分离：

```text
Extractor
→ 负责读取数据

Normalizer
→ 负责清理内容
```

---

# 六、Content Normalizer v0.3.0 范围

第一版只处理通用、确定性高的清洗。

包括：

```text
1. 移除 script / style 内容
2. 移除 HTML comments
3. 移除 Gutenberg block comments
4. 处理基础 shortcode 噪音
5. wp_strip_all_tags()
6. HTML entity decode
7. 规范空白
8. 合并多余换行
```

---

# 七、Normalizer 明确不承诺

v0.3.0 不尝试完美解析：

```text
Elementor
Divi
WPBakery
所有第三方 Page Builder
所有动态 Shortcode
```

如果某个建站系统的重要业务数据存储在特殊 Meta 中：

> 应由未来专用 Extractor 负责。

---

# 九、排除内部 Post Type

不能把 WordPress / Builder 内部类型作为普通 Knowledge Source。

例如：

```text

oembed_cache

wp_template

wp_global_styles

```

具体排除列表在开发过程中可根据 WordPress 实际返回结果确认。

同时预留一个轻量 Filter：

```text
wpaic_discoverable_post_types
```

允许开发者调整发现结果。

# 十一、默认策略

所有 Source：

# Default OFF

原因：

- 内容权限明确；
- 防止博客文章被误当企业承诺；
- 避免意外读取不应进入 AI 的页面；
- 中小企业管理员更容易理解；
- 为后续 Token / Cost 控制提供基础。

---

# 十二、v0.3.0 暂不做“一键推荐来源”

例如：

```text
检测到 Product / FAQ / Solution
[一键启用]
```

这个体验以后可以增加。

但它不是 v0.3.0 的核心目标。

第一版先验证：

```text
Discovery
+
Enable / Disable
```

是否稳定。

# 十五、Taxonomy 策略

v0.3.0 可以读取：

# Public Taxonomies

但：

> Taxonomy 不直接拼进正文。

保存为独立结构。

例如：

```text
taxonomies:
{
    product_cat: [
        "Composite Decking",
        "Outdoor Decking"
    ]
}
```

这样：

- 不污染正文；
- Preview 可查看；
- 后续 Retrieval 决定是否使用；
- Structured Source 保持清晰。

# 十六、Meta 策略


Knowledge Source 唯一标识。

例如：

## source_type

来源类别。

第一版：


## object_id

---

## post_type

原始 WordPress 内容类型。

例如：

```text

```

---

## knowledge_type

长期可能用于表达：

```text

faq

```

但：

# v0.3.0 不开发 Mapping System。

```text

```

或由当前 Extractor 固定输出。

不增加：

```text

Per-post Override
```

---

## title

原始标题。

---

## excerpt

如果文章存在摘要则读取。

无摘要时：

> v0.3.0 不强制自动生成 AI 摘要。

可以为空。

---

## url

来源页面 URL。

Manual Knowledge：

```text

```

因为它不是前台页面。

---

## taxonomies

独立结构化 Taxonomy 数据。

Generic Source 可以包含。

Manual Knowledge 可以包含自己的 Category。

---

## structured_data

结构化业务字段。

v0.3.0 Generic Extractor：

```text
structured_data = []
```

保留这个字段是为了 v0.3.1 WEM Extractor。

例如未来：

```text
Model
Dimensions
Material
Length
Color
```

可以直接放入这里。

---

## content

经过：

```text
Content Normalizer
```

后的纯净正文。

---

## source_hash

v0.3.0 可以生成 Hash。

但：

# 不保存、不比较、不触发生命周期。

只是 Source 输出字段。

真正的：

```text
Old Hash
vs
New Hash
Rebuild
```

属于：

# v0.4.0

---

## updated_at

来源内容最后更新时间。

---

## status

WordPress Post Status。

Knowledge Source 正式使用时，只接受：

```text
publish
```

Preview 可以根据实际调试需求允许管理员查看当前内容，但不能把 Draft 当成正式 Knowledge。

---

# 二十一、Source Hash 计算原则

Hash 应尽量基于：

> AI 实际会看到的数据。

而不是简单使用：

```text
post_modified
```

建议概念上：

```text
SHA-256(
    title
    + excerpt
    + normalized content
    + taxonomies
    + structured_data
)
```

这样未来：

```text
AI-visible content changed
→ Hash changed
```

更加可靠。

v0.3.0 只输出。

v0.4.0 再正式使用。

# 二十三、Manual Knowledge 的职责

只用于保存：

> 网站原有业务内容体系无法自然表达，但 AI 客服需要知道的规则、政策、流程和说明。

# 二十四、Manual Knowledge 不是什么

```text

Solution 副本
FAQ 副本
Page 副本
```

如果网站已经存在：

```text
FAQ
```

应该通过网站原有 FAQ Knowledge Source 使用。

不要重复录入。

# 五十九、最终开发决策

v0.3.0 正式采用：

# Generic Knowledge Source Foundation

由以下六个核心能力组成：

```text
1. Post Type Discovery
2. Enable / Disable Sources
3. Generic Extractor
4. Content Normalizer
5. Manual Knowledge CPT
6. Minimal Source Preview
```

核心思想：

> **网站继续负责业务内容。**

> **Knowledge Source 层负责把允许的 WordPress 内容转换成干净、统一、可检查的 AI Knowledge Source。**

> **结构化业务系统通过后续 Extractor 渐进增强，而不是污染 Core。**
