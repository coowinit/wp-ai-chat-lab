# v0.4.0 — Knowledge Store & Lifecycle

> 在 v0.3.x 已经能够把 WordPress 内容稳定转换为 Unified Knowledge Source 之后，v0.4.0 开始解决下一层问题：**这些已经标准化的 Knowledge Source 如何可靠保存、同步、更新、停用与恢复。**

**版本：v0.4.0**  
**阶段：Knowledge Store & Lifecycle**  
**状态：Stage 1 Validation Passed / Stage 2 Code Implemented — Awaiting Real-world Validation**  
**前置版本：v0.3.1 — Structured Source Validation**

---

# 一、版本背景

截至 v0.3.1，项目已经完成两条基础链路。

AI Provider：

```text
WordPress
→ AI Manager
→ DeepSeek Provider
→ Unified Response
```

Knowledge Source：

```text
WordPress Content
→ Generic Extractor
→ Content Normalizer
→ Structured Field Resolver
→ Unified Knowledge Source
→ Source Hash
```

并且已经在真实网站验证：

```text
Generic WordPress Content
Manual Knowledge
Legacy Product Meta
WEM Content Fields
```

都可以进入统一 Knowledge Source。

但当前 Source 仍然是：

```text
按需生成
→ Preview
→ 请求结束
→ 不保存
```

这意味着后续 Retrieval 如果直接建立在当前模式上，每次搜索都可能重新读取 WordPress、清洗正文、解析结构化字段。

因此 v0.4.0 的任务是建立：

# 一个可重建、可同步、可追踪状态的 Knowledge Store。

---

# 二、这一版最重要的概念：Source of Truth ≠ Knowledge Store

v0.4.0 第一次会持久化 Knowledge Source，但必须继续坚持：

> **WordPress 业务内容仍然是唯一 Source of Truth。**

Knowledge Store 只是一个面向 AI 的派生 Read Model / Snapshot。

正确关系：

```text
WordPress Post / Meta / Taxonomy / Manual Knowledge
                ↓
          Source of Truth
                ↓
        Extract / Normalize
                ↓
        Knowledge Store
                ↓
         Future Retrieval
```

因此：

- 不允许管理员直接在 Knowledge Store 中编辑业务内容；
- Store 中的数据必须可以从 WordPress Source 重建；
- 删除 Store 不应导致 WordPress 原始业务数据丢失；
- WordPress 内容更新后，Store 应同步，而不是反向覆盖 WordPress。

这和“网站已有的数据不重复录入”并不冲突。

v0.4.0 的持久化是：

> **机器可重建的 AI 读取快照，而不是第二套业务后台。**

---

# 三、v0.4.0 只解决什么

本版本只解决：

```text
Unified Knowledge Source
        ↓
Knowledge Store
        ↓
Lifecycle
```

核心能力限定为：

```text
1. Knowledge Store Schema
2. Store Repository
3. Source Hash Comparison
4. Single-source Sync
5. Batch Initial Sync
6. Incremental Lifecycle Sync
7. Active / Inactive State
8. Minimal Store Admin / Diagnostics
```

本版本仍然：

```text
不做 Retrieval
不做 Chunk
不做 Embedding
不做 Vector
不做 RAG
不调用 DeepSeek 生成答案
不做前台 Chat
```

---

# 四、为什么 v0.4.0 开始允许一个自定义数据库表

v0.3.x 一直坚持：

```text
Custom Database Tables = 0
```

因为当时 Knowledge Source 只是实时 Preview，没有持久化需求。

进入 v0.4.0 后，Store 需要：

```text
唯一 Source ID
Hash
Active / Inactive
结构化数据
标准化正文
同步时间
Lifecycle 状态
```

如果继续使用 CPT / Post Meta 存储派生 AI 数据，会产生：

- 与业务内容模型混在一起；
- Post Meta 行数快速膨胀；
- 后续 Retrieval 查询困难；
- Knowledge Store 与 WordPress Source 职责混淆。

因此 v0.4.0 建议正式引入：

```text
1 张 Knowledge Store 自定义表
```

表名：

```text
{$wpdb->prefix}wpaic_knowledge_store
```

原则：

> 一张表先解决 Store，不提前建立 Chunk、Embedding、Log 等附加表。

# 五、Knowledge Store 数据模型

建议第一版字段：

```text
id
source_id
source_type
object_id
post_type
knowledge_type

title
excerpt

structured_data
content

source_hash
source_status
store_status
inactive_reason

source_updated_at
last_action
last_checked_at
created_at
updated_at
```

## 1. 身份字段

```text
source_id
```

继续直接复用 v0.3.x 的稳定 Source ID，例如：

```text
wordpress_post_2413
manual_8764
```

数据库中建立 UNIQUE KEY：

```text
source_id UNIQUE
```

因此同一个 Source 不允许生成重复 Store Row。

---

## 2. AI-visible Snapshot

直接保存当前 Unified Knowledge Source 中真正需要的字段：

```text
title
excerpt
url
taxonomies
structured_data
content
source_hash
```

其中：

```text
taxonomies
structured_data
```

第一版继续使用 `wp_json_encode()` 后保存到 `LONGTEXT`。

暂时不依赖 MySQL JSON 类型，以保持 WordPress 主机兼容性。

---

## 3. Source Status 与 Store Status 分开

这是 v0.4.0 的关键设计。

Source Status：

```text
publish
draft
private
trash
deleted
...
```

表示 WordPress Source 当前是什么状态。

Store Status：

```text
active
inactive
```

表示：

> 这条 Store Row 是否允许被未来 Retrieval 使用。

因此：

```text
source_status = publish
store_status  = active
```

才属于正式 AI Knowledge。

---

# 六、Source Hash 与 Lifecycle Eligibility 必须分开

v0.3.x 已经真实验证：

```text
publish → draft
```

如果 AI-visible 内容没有变化，Source Hash 可以保持不变。

这说明：

> **Hash 只判断知识内容是否变化。**

但：

```text
publish → draft
```

即使 Hash 不变，这条 Source 也已经不应该继续参与 Retrieval。

因此 v0.4.0 必须同时判断两个维度：

```text
A. Content Changed?
→ source_hash

B. Still Eligible?
→ publish / enabled / exists
```

不能写成：

```text
Hash 没变
→ 什么都不做
```

否则 Draft / Trash / Disabled Source 会错误保留在正式 Knowledge 中。

---

# 七、Lifecycle Action

v0.4.0 定义六种最小动作：

```text
created
updated
unchanged
reactivated
deactivated
error
```

## 1. Create

条件：

```text
Store 中不存在 source_id
+
Source 当前 eligible
```

结果：

```text
INSERT
store_status = active
last_action = created
```

---

## 2. Unchanged

条件：

```text
Store 已存在
+
Source eligible
+
Hash 相同
+
Store 已 active
```

结果：

```text
不重写正文快照
更新 last_checked_at
last_action = unchanged
```

---

## 3. Update

条件：

```text
Store 已存在
+
Source eligible
+
Hash 改变
```

结果：

```text
UPDATE Snapshot
source_hash = new hash
last_action = updated
store_status = active
```

---

## 4. Deactivate

典型条件：

```text
publish → draft
publish → trash
Source 被删除
Post Type 不再启用为 Knowledge Source
Source 当前不存在
```

结果：

```text
保留 Store Snapshot
store_status = inactive
inactive_reason = ...
last_action = deactivated
```

第一版**不直接 DELETE Row**。

原因：

- 便于调试；
- 便于重新发布后快速恢复；
- 便于观察 Lifecycle；
- 避免误删后完全失去上下文。

---

## 5. Reactivate

条件：

```text
Store 已 inactive
+
Source 再次 eligible
```

结果：

```text
重新生成当前 Source
更新 Snapshot / Hash
store_status = active
inactive_reason = empty
last_action = reactivated
```

---

## 6. Error

同步失败时：

```text
不破坏已有 Store Snapshot
last_action = error
```

第一版不增加 Error Log Table。

错误直接通过管理员界面 / AJAX Response 显示即可。

---

# 八、Inactive Reason

第一版建议只保留少量可理解原因：

```text
not_published
source_disabled
source_deleted
source_missing
```

不要建立复杂状态机。

未来 Retrieval 只查询：

```text
store_status = active
```

而 `inactive_reason` 主要用于管理员诊断。

# 十、Schema 安装与升级策略

不能只依赖插件 Activation Hook。

因为真实使用中经常是：

```text
v0.3.1
→ 直接覆盖升级到 v0.4.0
```

WordPress 不一定重新触发 Activation。

因此建议新增：

```text
WPAIC_DB_VERSION
```

例如：

```text
1.0
```

以及：

```text
wpaic_db_version
```

Option。

运行：

```text
maybe_upgrade()
```

逻辑：

```text
当前 DB Version < WPAIC_DB_VERSION
→ dbDelta()
→ 更新 wpaic_db_version
```

Activation 也调用同一套 Installer。

原则：

> 表结构安装必须幂等，覆盖升级不能依赖“先停用再激活”。

# 十一、Deactivate / Uninstall 数据策略

## Deactivate

停用 WP AI Chat Lab：

```text
不删除 Knowledge Store
不删除 Options
不修改 WordPress Source
```

重新激活以后继续使用。

## Uninstall

v0.4.0 暂时：

```text
不自动 DROP Knowledge Store
```

因为 Knowledge Store 虽然可重建，但自动删除数据库数据属于高风险操作。

未来如果需要，可以单独设计：

```text
Delete plugin data on uninstall
```

明确设置项。

本版本不做。

# 十四、Eligibility 规则

## 普通 WordPress Content

必须同时满足：

```text
Post Type 已启用为 Knowledge Source
+
post_status = publish
+
Source 存在
```

才是 active Knowledge。

## Manual Knowledge

`wpaic_knowledge` 不依赖普通 Source Enable Checkbox。

只要：

```text
post_status = publish
```

就可以进入 Store。

## Draft / Trash / Deleted

统一变为：

```text
inactive
```

而不是物理删除 Row。

# 十五、同步策略：Initial Sync 与 Incremental Sync 分开

这是 v0.4.0 的另一个关键设计。

## A. Initial / Full Sync

用于：

```text
第一次建立 Knowledge Store
新增一个 Knowledge Source 类型
人工希望重新对齐 Store
```

后台提供：

```text
同步全部知识
```

但不要在一个 HTTP Request 中处理整个网站。

建议 AJAX Batch：

```text
每批 20~25 条
```

流程：

```text
Start
→ Batch 1
→ Batch 2
→ ...
→ Reconcile
→ Done
```

管理员可以看到：

```text
Processed
Created
Updated
Unchanged
Deactivated
Errors
```

不引入 Cron / Queue。

第一版保持可见、可调试。

---

## B. Incremental Sync

初始同步完成以后，日常修改不应该每次重新扫描全站。

建议监听 WordPress 内容生命周期。

优先使用：

```text
wp_after_insert_post
```

原因：

> 它发生在正常 Post 保存流程较后的位置，更适合等待旧 Meta Box / WEM 字段先完成保存。

同步时继续跳过：

```text
Revision
Autosave
Internal Post Type
```

同时处理：

```text
trash / delete / status transition
```

目标：

```text
编辑一条 Product
→ 只同步这一条 Product
```

而不是：

```text
编辑一条 Product
→ 重扫全站
```

---

# 十六、Source Enable / Disable 与 Store

v0.3.0 已有：

```text
Knowledge Source Enable / Disable
```

v0.4.0 后必须定义其生命周期含义。

## Disable

例如：

```text
Product ☑
→ Product ☐
```

现有 Product Store Rows 应：

```text
store_status = inactive
inactive_reason = source_disabled
```

不直接 DELETE。

## Re-enable

重新启用后：

```text
不会在设置保存请求中同步几百条文章
```

而是提示：

```text
Knowledge Store needs sync
```

管理员执行一次 Batch Sync 后重新 Active。

这样可以避免保存设置时长时间阻塞。

---

# 十七、Full Sync Reconciliation

Full Sync 不仅是 Create / Update。

最后必须做 Reconcile：

```text
Store 中 active
但 WordPress 当前已不存在 / 未 publish / Source 已 disabled
```

→ Deactivate。

因此 Full Sync 的最终意义是：

> **让 Store 与当前正式 Knowledge Source 集合重新一致。**

# 十九、为什么不做 Store Editor

Knowledge Store 页面不能出现：

```text
直接编辑 Title
直接编辑 Content
直接编辑 Structured Data
```

否则会形成第二个 Source of Truth。

正确操作只能是：

```text
修改 WordPress 原始内容
→ Sync
→ Store 更新
```

Manual Knowledge 也应该去：

```text
AI 补充知识 CPT
```

修改，而不是改 Store Row。

正式封版前至少完成：

```text

5. 修改 Legacy Structured Data → updated
6. 修改 WEM Structured Data → updated

9. draft → publish → reactivated
10. trash / delete → inactive
11. disabled Source Type → inactive
12. Manual Knowledge 可以同步
13. Full Sync 不产生重复 source_id
14. Full Sync 能 Reconcile stale rows
15. Incremental Save 只更新当前 Source
16. Plugin deactivate / reactivate 不丢 Store
17. Preview / Store 不调用 DeepSeek
18. 不建立 Chunk / Embedding / Vector
```
