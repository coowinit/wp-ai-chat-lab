# v0.3.1 — Structured Source Validation

> 在 v0.3.0 已经建立的 Generic Knowledge Source 基础上，验证 **同一套 Knowledge Source 架构能否同时兼容旧站 functions.php 自定义字段与新站 WEM Content Fields 字段体系**。

**版本：v0.3.1**  
**阶段：Structured Source Validation**  
**状态：First Code Build — Legacy Product Validation Pending**  
**前置版本：v0.3.0 — Knowledge Source Foundation**

---

# 一、版本背景

v0.3.0 已经完成：

```text
WordPress Content
→ Post Type Discovery
→ Enable / Disable
→ Generic Extractor
→ Content Normalizer
→ Unified Knowledge Source
→ Source Preview
```

真实环境已经验证：

```text
FAQ
Product
Post
Manual Knowledge
```

其中 Product 已经证明：

```text
Generic Product
→ Title / Excerpt / Taxonomies / Normalized Content
→ structured_data = []
```

因此 v0.3.1 的任务不是重新设计 Knowledge Source，而是回答下一个问题：

> **如何让 WordPress 已有的可信结构化业务字段进入 structured_data，同时不破坏 Generic Source，也不要求所有旧网站先迁移到新的字段插件？**

---

# 二、为什么版本名称从 WEM Structured Source Validation 调整为 Structured Source Validation

v0.3.0 封版时，最初计划是：

```text
v0.3.1
→ WEM Structured Source Validation
```

但对真实旧站代码进行兼容性检查后发现，大量现有网站并没有安装 WEM Content Fields。

旧站通常采用：

```text
functions.php
→ register_post_type()
→ add_meta_box()
→ 自定义 fields[]
→ update_post_meta()
```

而新站采用：

```text
WEM Content Types
+
WEM Content Fields
→ Field Groups / Field Definitions
→ registered post meta
```

这两种实现方式不同，但对 AI Knowledge 来说，本质都是：

```text
某个 Post Type
+
一组有明确业务语义的结构化字段
```

因此 v0.3.1 不应把“WEM Field Group”当作架构前提。

新的版本目标调整为：

# Structured Source Validation

WEM 只是结构化字段定义的一种来源。

# 三、真实兼容性样本

本版本设计基于两类真实旧站代码与当前 WEM 插件结构。

## 1. Legacy Product

旧 Product 使用：

```text
Post Type: products
```

典型业务字段包括：

```text
product_number    → Product Model
product_size      → Product Dimension
```

同时还存在：

```text
product_pic01
product_pic02
product_pic03
product_vrvideo
product_qrcode
product_video
pdf_ids
```

这些字段虽然都存储在 Post Meta 中，但并不全部适合作为 AI 文本知识。

---

## 2. Legacy Solution

旧 Solution 使用：

```text
Post Type: solutions
```

典型字段包括：

```text
solution_badge
solution_model
solution_dimension
solution_morelink
solution_pic01 ~ solution_pic05
solution_vrvideo
solution_qrcode
solution_vrvideo_before
solution_pdf_ids
```

Product 与 Solution 的旧代码模式高度一致，证明 Legacy Profile 可以作为一种可复用的字段定义来源，而不是只为单个 Product 页面做特殊兼容。

---

## 3. Modern WEM Content Fields

新 WEM 字段系统拥有明确的字段定义层，可描述：

```text
Field Group
├── key
├── title
├── post_types[]
└── fields[]
```

字段定义可以提供：

```text
field key
meta key
label
type
options
post type relation
```

因此新站可以通过 WEM Registry 获得结构化字段 Schema，而无需在 AI 插件中重新定义所有 Meta Key。

---

# 四、核心结论：Schema 不等于 AI Allowlist

这是 v0.3.1 最重要的设计原则。

一个字段存在，并不代表它应该进入 AI Knowledge。

例如旧 Solution 中这些字段技术上都是 text：

```text
solution_model
solution_dimension
solution_morelink
solution_vrvideo
solution_vrvideo_before
solution_pdf_ids
```

但它们的 AI 知识价值明显不同。

因此必须明确区分：

```text
Available Structured Fields
        ↓
AI Field Allowlist
        ↓
Structured Knowledge
```

不能使用：

```text
所有 Post Meta
→ AI
```

也不能使用：

```text
所有 text 字段
→ AI
```

# 七、继续复用 v0.3.0，而不是重写 Generic Extractor

v0.3.0 已经提供：

```text
wpaic_knowledge_source
```

扩展点。

因此 v0.3.1 的理想实现是：

```text
Generic Extractor
→ Unified Source
→ wpaic_knowledge_source
→ Structured Enhancer
→ structured_data
```

而不是：

```text
WEM Extractor
重新读取 Title

重新读取 Taxonomy
重新读取 Content
重新构建整个 Source
```

如果 v0.3.1 可以通过轻量增强层完成，而无需大改 v0.3.0 Core，则说明 v0.3.0 的 Knowledge Source 架构经第二个真实场景验证后仍然成立。

# 八、Normalized Field Definition

不同 Provider 必须先转换成统一字段定义。

建议内部结构：

```text
knowledge_key
meta_key
label
type
provider
```

例如旧站 Product：

```text
knowledge_key: product_model
meta_key:      product_number
label:         Product Model
type:          text
provider:      legacy
```

新 WEM Product 可能使用不同 Meta Key，但只要语义相同，就映射到同一个：

```text
knowledge_key: product_model
```

这样下游不需要知道：

```text
旧站 Meta Key 是什么
新站 Meta Key 是什么
字段来自 functions.php 还是 WEM
```

---

# 九、为什么必须引入稳定 knowledge_key

如果直接把原始 Meta Key 当作 structured_data Key：

旧站可能得到：

```text
product_number
```

新站可能得到：

```text
_wem_cf_product_number
```

虽然两者表达同一个业务概念，但 AI Knowledge Schema 会变成两个不同字段。

因此 v0.3.1 应统一为业务语义 Key：

```text
product_model
product_dimension
```

最终 structured_data 与底层 Meta Key 解耦。

这是兼容旧站和新站的关键。

# 十、Legacy Profile Provider

旧站不解析 functions.php 源码。

明确不采用：

```text
读取 PHP 文件
→ 正则查找 fields[]
→ 猜 Meta Key
```

原因：

```text
1. 不同主题实现方式可能不同
2. 不同 Generator 版本可能不同
3. 可能使用 ACF / Meta Box / 手写代码
4. PHP 源码解析脆弱
5. 不值得为了 AI 引入高维护成本
```

正确策略是：

# Explicit Legacy Profile

# 十一、v0.3.1 初始 Legacy Product Profile

第一版只保留高确定性、明显属于业务知识的字段。

建议：

```text
products
├── product_number
│   ├── knowledge_key: product_model
│   └── label: Product Model
│
└── product_size
    ├── knowledge_key: product_dimension
    └── label: Product Dimension
```

明确不默认加入：

```text
product_pic01
product_pic02
product_pic03
product_vrvideo
product_qrcode
product_video
pdf_ids
```

原因不是这些字段永远无价值，而是：

> v0.3.1 只验证可靠的文本型结构化业务知识。

---

# 十二、Legacy Profile 扩展方式

第一阶段 Profile 建议使用：

```text
PHP Array
+
Developer Filter
```

而不是数据库配置 UI。

建议提供类似：

```text
wpaic_legacy_structured_profiles
```

的扩展入口。

特殊老站可以增加：

```text
product_material
product_weight
solution_model
solution_dimension
```

而不修改 AI Core。

本版本不实现 Visual Field Mapper。

---

# 十三、WEM Definition Provider

新站如果安装 WEM Content Fields，则 Provider 可以读取 WEM 的运行时字段定义。

这里必须遵守两个原则：

## 1. WEM Registry 只负责告诉 AI 插件“有哪些字段”

例如：

```text
field key
meta key
label
type
options
post type
```

## 2. 是否进入 AI 仍由 WP AI Chat Lab Allowlist 决定

因此：

```text
WEM Field Registry
≠
AI Field Allowlist
```

即使字段类型是：

```text
text
textarea
editor
select
checkbox
```

也不能自动全部授权。

---

# 十四、WEM 字段类型处理原则

当字段已进入 AI Allowlist 后，v0.3.1 建议支持：

```text
text      → string
textarea  → normalized text
editor    → normalized text
select    → human-readable selected label
checkbox  → human-readable selected labels
```

暂不支持：

```text
image
file
```

原因：

```text
v0.3.1 不是多模态版本
v0.3.1 不解析 PDF / File 内容
```

---

# 十五、WEM Product Mapping 需要真实 Schema 后冻结

架构不依赖 Field Group，但具体 WEM Product 字段映射仍必须来自真实网站字段定义。

例如最终需要确认：

```text
某个 WEM Field Key
→ product_model

某个 WEM Field Key
→ product_dimension
```

不能依据字段名称猜测。

因此在进入代码实现前，应对一个真实 WEM Product Field Group 做一次 Schema Audit，并把最终 Mapping 写入本版本实现或测试 Profile。

这属于实现输入，不再是架构前提。

---

# 十六、Provider 冲突与迁移场景

某些网站未来可能同时存在：

```text
Legacy Meta
+
WEM Meta
```

例如正在从旧字段系统迁移到新字段系统。

v0.3.1 不增加复杂 Priority UI。

采用固定规则：

```text
1. WEM 有非空值 → 使用 WEM
2. WEM 无值 / 无定义 → 回退 Legacy
3. 同一个 knowledge_key 最终只输出一次
```

即：

```text
WEM
→ preferred

Legacy
→ fallback
```

这样既支持新站，也支持迁移期网站。

---

# 十七、Structured Data 最终输出格式

v0.3.1 不建议直接暴露底层 Meta Key。

建议：

```json
{
  "product_model": {
    "label": "Product Model",
    "value": "COC-09"
  },
  "product_dimension": {
    "label": "Product Dimension",
    "value": "219mm × 26mm"
  }
}
```

不建议：

```json
{
  "product_number": "COC-09",
  "_wem_cf_product_size": "219mm × 26mm"
}
```

因为后者把存储实现泄漏到了 Knowledge Schema。

---

# 十八、为什么最终 structured_data 不保存 provider / meta_key

`provider`、`meta_key` 对调试有价值，但不是 AI 业务知识。

因此最终 AI-visible 数据只保留：

```text
knowledge_key
label
value
```

内部 Resolver 可以知道：

```text
legacy
wem
meta_key
```

但不要为了调试信息增加 AI Token 消耗。

如果未来确实需要 Diagnostics，可以单独增加调试结构，而不是污染 structured_data。

---

# 十九、Structured Value Normalizer

结构化字段不能直接原样输出。

v0.3.1 建议：

```text
空值
→ 不输出

text
→ trim + scalar normalize

textarea
→ Content Normalizer

editor
→ Content Normalizer

select
→ stored value → option label

checkbox
→ stored values → option labels[]
```

明确不做：

```text
单位换算
产品参数推理
自动翻译
AI 补全
字段猜测
```

Structured Data 必须保持：

# Source-derived only

第一轮仅内置旧站 Product 两个高确定性字段：

```text
product_number

→ label: Product Model

product_size
→ knowledge_key: product_dimension
→ label: Product Dimension
```

最终 AI-visible `structured_data` 目标：

```json
{
  "product_model": {
    "label": "Product Model",
    "value": "COC-09"
  },
  "product_dimension": {
    "label": "Product Dimension",
    "value": "219mm × 26mm"
  }

```

本轮继续明确不读取：

```text
product_pic01 ~ product_pic03
product_vrvideo
product_qrcode
product_video
pdf_ids
```

实现仍然复用 v0.3.0 的：

```text
wpaic_knowledge_source
```

因此 Generic Extractor 没有为 Legacy Product 增加特殊分支。Structured Enhancer 在 Source Filter 阶段补充 `structured_data`，随后现有 `WPAIC_Knowledge_Source::prepare()` 自动重新计算 Source Hash。

本轮新增开发者扩展点：

```text
wpaic_legacy_structured_profiles
wpaic_structured_field_definitions
wpaic_structured_data
```

当前没有实现 WEM Definition Provider。只有 Legacy Product 最小链路在真实 WordPress 环境通过后，才进入第二个 Provider 验证。
