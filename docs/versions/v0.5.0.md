# v0.5.0 — Local Retrieval

> v0.4.0 已经解决“知识如何可靠保存和维护”。v0.5.0 开始解决下一层问题：**面对一个真实问题，如何在不调用 AI、不依赖 Embedding / Vector Database 的前提下，从 Knowledge Store 中找出最相关、最可信、可解释的 Knowledge Source。**

**版本：v0.5.0**  
**阶段：Local Retrieval**  
**状态：Design Ready — Awaiting Implementation**  
**前置版本：v0.4.0 — Knowledge Store & Lifecycle**

---

# 一、版本背景

截至 v0.4.0，项目已经形成完整 Knowledge Pipeline：

```text
WordPress Source
        ↓
Extract / Normalize
        ↓
Unified Knowledge Source
        ↓
Source Hash
        ↓
Knowledge Store
        ↓
Lifecycle
```

真实网站已经验证：

```text
Generic WordPress Content
Manual Knowledge
Legacy Product Structured Data
WEM Product Structured Data
```

都能稳定进入 Knowledge Store；同时：

```text
Initial Build
→ Full Sync

Whole-site Reconcile
→ Full Sync + Reconciliation

Daily Maintenance
→ Incremental Sync
```

已经成立。

但当前系统仍然不会回答：

> 用户问了一句话以后，Knowledge Store 中到底哪几条知识最相关？

因此 v0.5.0 的任务不是 AI Answer，而是建立：

# 一个透明、可解释、低成本的本地 Retrieval 层。

---

# 二、这一版最重要的原则：Retrieval ≠ Answer

v0.5.0 必须坚持：

```text
Question
↓
Retrieval
↓
Relevant Knowledge Sources
```

到这里停止。

本版本不做：

```text
Relevant Sources
↓
DeepSeek
↓
Natural Language Answer
```

那属于：

```text
v0.6.0 — Grounded AI
```

因此 Local Retrieval 的成功标准不是：

> AI 回答得像不像人。

而是：

> **给定一个真实问题，系统能否稳定把正确 Knowledge Source 排到前面，并明确解释为什么它排在前面。**

---

# 三、为什么继续坚持 Local Retrieval First

目前 Knowledge Store 的典型规模是：

```text
几十
几百
到低几千条 Knowledge Source
```

例如真实测试网站当前约：

```text
Active Knowledge ≈ 138
```

在这种规模下，直接进入：

```text
Embedding
Vector Database
External Vector Service
```

会过早引入：

- 额外 API 成本；
- Embedding 模型依赖；
- Vector Index 生命周期；
- Chunk 策略；
- Re-embedding；
- 第三方服务或复杂本地索引；
- 更难调试的相似度结果。

而 WordPress 企业站的很多问题本身具有非常强的词汇信号，例如：

```text
CWC-610 dimension
COC-09 size
sample policy
MOQ
fire resistant
composite decking slippery winter
```

其中：

```text
产品型号
标题
分类
FAQ 问题
Structured Data
```

往往已经提供非常强的本地检索线索。

因此 v0.5.0 先验证：

> **Lexical Retrieval + Field Weighting + Explainable Scoring 是否已经足够。**

只有真实测试证明它不足，再讨论 Embedding / Vector。

---

# 四、v0.5.0 只解决什么

本版本限定为：

```text
1. Query Normalization
2. Query Term Extraction
3. Candidate Recall
4. Active Knowledge Filtering
5. Weighted Local Scoring
6. Exact / Phrase / Field Boost
7. Top-K Retrieval
8. Score Breakdown
9. Retrieval Diagnostics / Playground
10. Quality Calibration
```

本版本明确不做：

```text
AI Answer
DeepSeek Retrieval Call
Prompt Builder
Grounding Gate
RAG
Chunk
Embedding
Vector Database
Fulltext Index
Conversation
Live Chat
Lead
Human Handoff
```

---

# 五、v0.5.0 不新增 Knowledge 数据副本

Retrieval 直接读取：

```text
{$wpdb->prefix}wpaic_knowledge_store
```

并且只读取：

```text
store_status = active
```

的正式 Knowledge。

不会：

```text
重新扫描 WordPress Post
重新运行 Extractor
重新 Normalize
重新读 Legacy / WEM Meta
```

正确关系：

```text
Question
↓
Local Retrieval
↓
Knowledge Store
↓
Active Rows
↓
Relevant Sources
```

这正是 v0.4.0 建立 Knowledge Store 的价值。

# 六、总体架构

建议 v0.5.0 建立以下最小链路：

```text
User Question
      ↓
Query Normalizer
      ↓
Query Terms
      ↓
Candidate Searcher
      ↓
Active Knowledge Candidates
      ↓
Local Scorer
      ↓
Score + Breakdown
      ↓
Top-K Results
      ↓
Retrieval Playground
```

建议核心组件：

```text
WPAIC_Retrieval_Query_Normalizer
WPAIC_Retrieval_Candidate_Searcher
WPAIC_Retrieval_Scorer
WPAIC_Local_Retriever
```

必要时可以再加入一个简单 Result Value Object / Array Contract，但不急着建立复杂 Interface Framework。

---

# 七、Query Normalizer

Retrieval 不能直接拿原始问题到处 `LIKE`。

第一步先得到稳定 Query Representation。

例如：

```text
原始：
What is the dimension of CWC-610?
```

Normalize：

```text
what is the dimension of cwc-610
```

Terms：

```text
cwc-610
dimension
```

第一版建议执行：

```text
Unicode lowercase
HTML entity decode
标点标准化
多余空白合并
保留字母 / 数字 / - / _ 等型号字符
基础停用词过滤
重复 Term 去重
```

但必须注意：

> Query Normalizer 不能把产品型号破坏掉。

例如：

```text
CWC-610
COC-09
TW-02
3D
219mm
```

必须尽量保留为稳定 Term。

---

# 八、第一版 Stop Words 必须非常克制

只过滤明显低价值的常见英语功能词，例如：

```text
what
is
the
of
a
an
to
for
in
on
and
```

不要建立巨大 NLP Stopword Dictionary。

原因：

- B2B 查询通常很短；
- 过度过滤可能误删产品语义；
- 第一版重点是透明和可调试。

建议提供 Filter：

```text
wpaic_retrieval_stop_words
```

以后按真实数据调整。

---

# 九、中英文 Query 的第一版策略

v0.5.0 不引入中文分词器。

第一版采用：

```text
A. 保留完整 normalized query
B. Unicode-aware token 提取
C. 英文 / 型号词汇优先按 token 参与评分
D. 中文连续文本至少保留完整 phrase 参与 substring recall
```

这意味着：

- 英文 B2B 查询是第一轮重点验证场景；
- 中文完整短语仍可以通过 phrase / substring 命中；
- 不承诺第一版达到专业中文搜索引擎分词质量。

只有真实测试证明中文 Retrieval 不足，再考虑：

```text
CJK n-gram
专用分词
Synonym Dictionary
```

而不是现在一次性加入。

---

# 十、Candidate Recall：先召回，再评分

不要直接把整个 Knowledge Store 全量加载到 PHP 后再比较。

建议两阶段：

```text
SQL Candidate Recall
↓
PHP Weighted Scoring
```

Candidate Search 只查询：

```text
store_status = active
```

第一版允许参与召回的字段：

```text
title
excerpt
taxonomies
structured_data
content
```

其中任意 Query Term / Phrase 命中即可进入 Candidate Pool。

第一版 SQL 继续采用：

```text
LIKE
```

不建立 FULLTEXT Index。

原因：

- 当前 Knowledge Store 规模较小；
- WordPress 主机兼容性最好；
- 可以先得到真实 Retrieval Benchmark；
- v0.5.0 再决定是否真的需要 FULLTEXT。

---

# 十一、Candidate Limit

必须限制 Candidate Pool。

建议默认：

```text
Candidate Limit = 100
```

这样即使未来 Knowledge Store 有几千条，也不会把大量 Longtext 全部送进 PHP Scorer。

建议提供 Filter：

```text
wpaic_retrieval_candidate_limit
```

第一版允许范围例如：

```text
20 ~ 200
```

---

# 十二、为什么 Scoring 必须在 PHP 层完成

如果一开始把所有权重直接写进复杂 SQL：

- 不容易解释；
- 不容易测试；
- 调整权重困难；
- MySQL 差异更明显；
- 很快演变成难维护的搜索 SQL。

第一版更适合：

```text
SQL
→ 只负责 Recall

PHP
→ 负责 Score
```

这样每条结果都可以输出：

```text
为什么匹配？
匹配了哪些字段？
哪些 Term 得了多少分？
```

---

# 十三、Weighted Field Scoring

第一版建议建立清晰的字段权重顺序：

```text
Structured Data
Title
Taxonomies
Excerpt
Content
```

原因：

## Structured Data

例如：

```text
product_model = CWC-610
product_dimension = 610*9mm
```

属于高可信业务字段。

因此产品型号精确命中 Structured Data 应拥有非常高权重。

## Title

标题通常是页面主题最强信号。

## Taxonomies

分类 / 标签提供主题范围信号。

## Excerpt

摘要提供页面核心描述。

## Content

正文信息最丰富，但同时噪音也最大，所以基础权重最低。

---

# 十四、第一版建议权重

设计初始值：

```text
Structured Data   8
Title             6
Taxonomies        4
Excerpt           3
Content           1
```

这些不是“真理”。

它们只是：

> 第一轮真实测试的可解释起点。

必须允许以后校准。

建议 Filter：

```text
wpaic_retrieval_field_weights
```

---

# 十五、Exact Match Boost

仅靠 Term Count 不够。

例如 Query：

```text
CWC-610 dimension
```

如果 Structured Data 中：

```text
product_model = CWC-610
```

这是非常强的信号。

所以第一版建议增加：

```text
Exact Term Match Boost
```

尤其针对：

```text
型号
编号
带数字的业务 Token
```

例如：

```text
CWC-610
COC-09
TW-02
```

应明显高于正文里偶然出现一次 `dimension`。

---

# 十六、Phrase Match Boost

原始 Query 的关键 Phrase 也应参与评分。

例如：

```text
composite decking slippery winter
```

如果某篇标题是：

```text
Will Composite Decking Become Slippery in Winter?
```

即使词序不是完全一样，也应该得到较高 Title / Phrase 分。

第一版可以保持简单：

```text
完整 normalized query substring
重要 term sequence substring
```

不做复杂 NLP Phrase Parser。

---

# 十七、Coverage Bonus

一个 Source 如果只匹配 Query 的一个普通 Term：

```text
dimension
```

不应该和同时匹配：

```text
CWC-610
+
dimension
```

得到相同评价。

因此第一版建议加入：

```text
Query Term Coverage
```

例如：

```text
2 / 2 terms matched
→ Coverage Bonus

1 / 2 terms matched
→ 无或较低 Bonus
```

这样可以降低“只因为一个常见词就排到前面”的问题。

---

# 十八、不要加入 Recency Boost

v0.5.0 第一版不建议：

```text
越新的内容
→ 分数越高
```

原因：

企业知识的“新”不等于“相关”。

例如：

```text
2024 年产品规格
```

可能比：

```text
昨天发布的一篇泛博客
```

更适合回答产品尺寸问题。

因此：

```text
source_updated_at
```

可以作为诊断信息，但第一版不参与相关性评分。

---

# 十九、不要默认给某种 Source Type 加隐藏优先级

例如不要写：

```text
Product 永远 > Post
Manual Knowledge 永远 > FAQ
```

因为不同 Query 场景并不成立。

第一版应该让：

```text
匹配证据
```

决定排名，而不是内容类型身份。

如果以后业务确认某类 Source 需要优先，再通过显式规则加入。

---

# 二十、Result Contract

每个 Retrieval Result 建议返回：

```text
source_id
object_id
post_type
knowledge_type
title
url
score
rank
matched_terms
matched_fields
score_breakdown
source_hash
```

第一版不需要把完整 `content` 默认全部返回给 UI。

Playground 可以显示一个短 Snippet。

未来 v0.6.0 Prompt Builder 再根据 Top Result 获取完整 Snapshot。

---

# 二十一、Score Breakdown 是必须项

Local Retrieval 最大优势之一就是：

# 可解释。

例如：

```text
Question:
What is the dimension of CWC-610?
```

Result：

```text
CWC-610 Product
Score: 92

Matched:
structured_data.product_model: CWC-610
structured_data.product_dimension: dimension context
title: CWC-610

Coverage:
2 / 2
```

管理员应该能够看到：

> 它为什么排第一？

如果 Retrieval 结果不合理，我们才能快速调整。

---

# 二十二、Top-K

第一版建议：

```text
Default Top K = 5
```

Playground 可以允许：

```text
3 / 5 / 10
```

但不要把它变成复杂设置页。

未来 AI Prompt 不应该默认携带几十条 Knowledge。

因此 v0.5.0 必须从一开始形成：

```text
Candidate Pool
→ Ranking
→ Top K
```

意识。

建议 Filter：

```text
wpaic_retrieval_top_k
```

---

# 二十三、Retrieval Strength

v0.5.0 可以返回一个诊断级 Strength：

```text
strong
medium
weak
none
```

但必须明确：

> 这还不是 v0.6.0 的 Grounding Gate。

它只是帮助我们观察本地检索质量。

第一版阈值不要写成不可修改的业务真理。

应通过真实 Query Set 校准。

---

# 二十四、No Match 是正常结果

这是非常重要的设计原则。

Retrieval 不应该为了“必须给结果”而返回明显不相关内容。

正确结果允许：

```text
Question
↓
No Reliable Local Match
```

这比：

```text
随便找一篇勉强相关页面
```

更安全。

未来 v0.6.0 才能基于这个信号决定：

```text
是否允许 AI 回答
```

---

# 二十五、Query Alias / Synonym 第一版不自动生成

例如：

```text
size ↔ dimension
decking ↔ deck
MOQ ↔ minimum order quantity
```

这些确实有价值。

但 v0.5.0 第一版不使用 AI 自动扩展 Query。

可以预留轻量 Filter：

```text
wpaic_retrieval_query_terms
```

开发者可以显式补充少量业务 Alias。

是否需要正式 Synonym Dictionary，必须根据真实 Retrieval 失败案例决定。

---

# 二十六、Structured Data 的特殊价值

v0.3.1 特意建立：

```text
knowledge_key
```

现在 v0.5.0 会第一次真正消费这个价值。

例如不同网站底层：

```text
Legacy:
product_number

WEM:
_wem_cf_product_model
```

在 Store 中统一为：

```text
product_model
```

因此 Query：

```text
CWC-610
```

Retrieval 根本不需要知道底层来源。

它只搜索统一的：

```text
structured_data
```

这正是 Structured Knowledge Schema 的长期价值。

---

# 二十七、只检索 active Store Row

这是硬规则。

SQL 必须始终带：

```text
store_status = active
```

因此：

```text
draft
trash
source_disabled
source_deleted
source_missing
```

留下的 inactive Historical Snapshot：

> **不能进入 Retrieval Candidate。**

这会直接验证 v0.4.0 Lifecycle 与 v0.5.0 Retrieval 是否真正衔接正确。

---

# 二十八、Retrieval Playground

v0.5.0 应新增一个轻量后台页：

```text
WP AI Chat Lab
→ 本地检索
```

页面只需要：

```text
Question
Top K
Search
```

结果显示：

```text
Normalized Query
Terms
Candidate Count
Elapsed Time
Retrieval Strength
Top Results
```

每个 Result 展示：

```text
Rank
Score
Title
Post Type
Source ID
Matched Fields
Matched Terms
Score Breakdown
Snippet
URL
```

不要加入聊天 UI。

不要加入 AI Answer。

---

# 二十九、Playground 不应该修改 Knowledge Store

Retrieval 页面只读。

它不能：

```text
Save Source
Update Hash
Run Full Sync
Modify Store Status
```

如果数据不对：

```text
回到 WordPress Source
或
Knowledge Store Sync
```

处理。

这继续保持：

```text
Source / Store / Retrieval
```

三层职责分离。

---

# 三十、性能基线

v0.5.0 不追求搜索引擎级性能。

第一版目标：

```text
几百条 Knowledge Store
→ 本地检索明显低于一次外部 AI API 调用延迟
```

真实测试应记录：

```text
Candidate Count
Scored Count
Elapsed ms
```

如果：

```text
138 条
几百条
1000 条
```

都能轻松运行，就不应为了理论性能提前引入复杂索引。

---

# 三十一、为什么暂时不做 FULLTEXT

FULLTEXT 并非否定。

只是现在还没有证据证明需要。

第一版先运行：

```text
LIKE Recall
+
PHP Scoring
```

真实测试后，如果出现：

```text
Store 规模增大
LIKE Candidate Recall 明显变慢
```

再考虑：

```text
MySQL FULLTEXT
```

如果出现：

```text
词汇不匹配但语义高度相关的问题大量失败
```

再考虑：

```text
Embedding / Vector
```

这两个问题不能混为一谈。

---

# 三十二、第一轮真实 Query Set

建议 v0.5.0 不只测试“能搜到”，而是建立一个很小的 Retrieval Benchmark。

至少覆盖：

```text
A. Product Model
B. Product Attribute
C. FAQ
D. Blog Topic
E. Manual Policy
F. No-match Question
```

例如真实站点可以使用：

```text
1. CWC-610 dimension
2. CWC-610
3. Is your product fire resistant?
4. composite decking slippery winter
5. sample policy / MOQ（如果 Manual Knowledge 中有）
6. 一个知识库明确不存在的问题
```

---

# 三十三、测试 Product Model 的意义

这是 Structured Data 最强场景。

Query：

```text
CWC-610 dimension
```

预期：

```text
包含 product_model = CWC-610 的 Product
```

排名应显著领先泛 Blog / FAQ。

如果这一项都做不好：

> Scoring Model 需要调整，不能进入 Grounded AI。

---

# 三十四、测试 FAQ 的意义

例如：

```text
Is your product fire resistant?
```

预期：

```text
FAQ Question / FAQ Title
```

应获得很强的 Title / Phrase Match。

这可以验证：

> Retrieval 不只是为 Product Structured Data 服务。

---

# 三十五、测试 Blog Topic 的意义

例如：

```text
composite decking slippery winter
```

应该把相关博客排到前面。

这主要验证：

```text
Title
Excerpt
Content
Taxonomy
```

的组合权重。

---

# 三十六、测试 Manual Knowledge 的意义

例如：

```text
sample policy
MOQ
quotation process
```

如果 Manual Knowledge 中确实存在对应知识：

应能够正常排名。

不能因为它是：

```text
wpaic_knowledge
```

就被排除或默认降权。

---

# 三十七、测试 No-match 的意义

刻意问一个 Knowledge Store 中不存在的问题。

目标不是：

```text
一定返回 5 条结果
```

而是观察：

```text
Top Score 是否足够低
Retrieval Strength 是否 weak / none
```

这会为 v0.6.0 Grounding Gate 提供最重要的数据。

---

# 三十八、第一版 Scoring 不直接决定“能否回答”

v0.5.0 可以产生：

```text
score
strength
```

但不能把它包装成：

```text
AI 可以回答 / AI 不可以回答
```

原因：

Grounding Gate 还要考虑：

```text
Top result quality
Multiple-source conflict
Coverage
Question intent
Business fallback
```

这些属于 v0.6.0。

---

# 三十九、建议的 Filter 扩展点

第一版只保留少量真正有价值的扩展点：

```text
wpaic_retrieval_stop_words
wpaic_retrieval_query_terms
wpaic_retrieval_candidate_limit
wpaic_retrieval_field_weights
wpaic_retrieval_top_k
wpaic_retrieval_results
```

不要建立视觉化 Scoring Builder。

# 四十、安全与权限

Retrieval Playground 属于后台诊断工具。

第一版继续要求：

```text
manage_options
```

并使用：

```text
Nonce
```

前台 Public Retrieval API 暂不开放。

原因：

> 先把检索质量验证清楚，再决定前台 Contract。

---

# 四十一、数据暴露边界

Playground 可以显示 Knowledge Store 中已经属于 AI-visible Snapshot 的数据。

但不要额外读取：

```text
任意 Post Meta
Elementor Meta
SEO Meta
内部管理字段
```

也就是说：

> Retrieval 的数据边界不能比 Knowledge Store 更宽。

---

# 四十二、v0.5.0 不新增自定义数据库表

当前：

```text
Knowledge Store Table = 1
```

v0.5.0 第一版继续保持：

```text
Retrieval Table = 0
Chunk Table = 0
Embedding Table = 0
Vector Table = 0
```

也不建立 Query Log Table。

测试 Query 暂时只在当前页面显示，不持久化。

---

# 四十三、是否记录 Retrieval Query

第一版：

# 不记录。

原因：

- 目前只是后台 Lab；
- 不需要为了诊断先建立日志系统；
- 后续真正前台 Chat 时，Query 会自然属于 Conversation / Message。

因此 v0.5.0 不新增 Retrieval Logs。


# 四十六、Acceptance Criteria

v0.5.0 正式封版前至少验证：

```text
1. Retrieval 只查询 active Store Row
2. inactive / deleted / disabled Snapshot 不进入 Candidate
3. Product Model Query 可以找到正确 Product
4. Product Attribute Query 可以找到正确 Product
5. FAQ Query 可以找到正确 FAQ
6. Blog Topic Query 可以找到正确 Post
7. Manual Policy Query 可以找到正确 Manual Knowledge
8. No-match Query 不强制伪造高相关结果
9. Candidate Limit 生效
10. Top-K 生效
11. Score Breakdown 可解释
12. 相同 Query 重复 Retrieval 排名稳定
13. Retrieval 不修改 Knowledge Store
14. Retrieval 不触发 Full Sync / Incremental Sync
15. Retrieval 不调用 DeepSeek
16. 不新增 Chunk / Embedding / Vector
17. 不新增 Retrieval 自定义表
18. 几百条 Knowledge Store 下响应速度可接受
```

# 四十八、对 v0.6.0 的影响

如果 v0.5.0 Local Retrieval 真实验证成功：

```text
Question
↓
Reliable Relevant Sources
```

那么 v0.6.0 才进入：

```text
Relevant Sources
↓
Grounding Gate
↓
Prompt Builder
↓
DeepSeek
↓
Grounded Answer
```

此时 AI 不需要：

```text
自己搜索整个 WordPress
自己猜知识
自己决定哪些页面相关
```

它只接收 Retrieval 已经筛选出的证据。

# 四十九、如何判断未来是否需要 Vector

v0.5.0 完成后，不根据“Vector 更高级”决定升级。

应该看真实失败类型。

如果失败主要是：

```text
SQL LIKE 太慢
```

解决方向可能是：

```text
FULLTEXT / Index
```

如果失败主要是：

```text
用户用词与网站知识用词完全不同
但语义相同
```

才真正属于：

```text
Semantic Retrieval
Embedding / Vector
```

这两个问题必须分开判断。

# 五十、最终开发合同

v0.5.0 的一句话定义：

> **从 Knowledge Store 中，以透明、可解释、低成本的本地词汇检索和字段加权方式，为一个真实问题找出最相关的 Top-K Knowledge Source；本版本只负责找证据，不负责生成答案。**

必须坚持：

```text
Knowledge Store = Retrieval Source
Active Only
Recall Before Ranking
Structured Data > Generic Content Weight
Explainable Score
Top-K
No Match Is Valid
Local First
No AI Call
No Vector Yet
```

如果开发过程中出现：

```text
DeepSeek Answer
Prompt Builder
Chat UI
Vector Database
```

说明已经越过 v0.5.0 边界，应停止扩展。
