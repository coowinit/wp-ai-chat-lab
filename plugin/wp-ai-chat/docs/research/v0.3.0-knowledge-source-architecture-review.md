# WP AI Chat Lab v0.3.0：Knowledge Source 架构决策草案

> 用于 Grok、DeepSeek、Gemini 等模型进行独立评审。  
> 当前状态：**设计讨论阶段，尚未定稿，尚未进入 v0.3.0 代码开发。**

---

# 一、背景

WP AI Chat Lab 是一个长期迭代的 WordPress AI Chat 项目。

目前已经完成：

- `v0.1.0`：Concept & Architecture Baseline
- `v0.2.0`：AI Provider Foundation
  - AI Provider Interface
  - AI Manager
  - DeepSeek Provider
  - API Key / Model / Connection Test
  - Minimal AI Test
  - Unified Response
  - Error Model
  - 实际 WordPress 环境测试通过

接下来准备进入：

# `v0.3.0 — Knowledge Sources`

这一版本第一次真正涉及：

> **WordPress 网站中的哪些内容，应该成为 AI 可以使用的知识？**

这个问题非常重要，因为它会直接影响：

- 插件是否容易开发；
- 是否适合中小企业使用；
- 是否能适配不同 WordPress 网站；
- 是否会重复维护数据；
- AI Knowledge 是否干净可靠；
- 后续 Retrieval / Grounding / RAG 是否容易实现；
- 后续能否扩展 WooCommerce / ACF / Meta Box / WEM 等系统；
- 插件是否会逐渐复杂化。

---

# 二、核心目标

希望找到一个同时满足以下条件的方案：

1. **开发复杂度可控**
2. **中小企业管理员容易理解和使用**
3. **尽量复用 WordPress 已有内容**
4. **避免重复维护 Product / FAQ / Solution**
5. **可以适配不同 CPT**
6. **支持结构化字段**
7. **不会把无关 Post Meta 污染 AI Knowledge**
8. **未来可以扩展 WooCommerce / ACF / Meta Box**
9. **Knowledge 与 Chat 解耦**
10. **后续 Retrieval / Grounding 易于维护和升级**

# 五、当前最核心的问题

我们需要决定：

> **AI Knowledge 到底应该如何从 WordPress 内容中获得？**

这里至少有四种方案。

---

# 六、方案 A：AI 插件自己创建 Product / Solution / FAQ

例如：

```text
AI Product
AI Solution
AI FAQ
```

AI 插件拥有自己的业务数据。

## 优点

- 数据完全由插件控制
- 字段统一
- AI Knowledge 非常容易读取
- 开发逻辑直观

## 缺点

最大问题是：

```text
WordPress Product
+
AI Product
```

形成两套数据。

例如：

```text
网站产品长度：
2.2m / 2.9m / 3.6m / 5.4m

AI Product：
2.2m / 2.9m / 3.6m
```

很容易发生不同步。

## 评价

与以下原则冲突：

> Single Source of Truth

### 当前倾向

**不推荐。**

---

# 七、方案 B：直接绑定现有 WEM 内容类型

插件固定支持：

```text
product
solution
faq
```

并直接读取固定字段：

```text
wem_dimensions
wem_material
wem_length
wem_color
...
```

## 优点

- 对当前网站开发最快
- 字段语义最明确
- AI Knowledge 质量高
- 最容易尽快完成真实网站验证

## 缺点

插件会逐渐变成：

> WEM 专用 AI 插件

换一个 WordPress 网站，如果使用：

```text
products
item
portfolio
woocommerce product
ACF fields
```

就不能直接使用。

## 评价

适合作为：

> **一个测试 Adapter**

不适合作为：

> 核心架构。

### 当前倾向

**不作为 Core，但可以后续实现 WEM Adapter。**

---

# 八、方案 C：完全通用 Field Mapping Builder

后台允许管理员：

```text
添加知识来源
→ 选择 Post Type
→ 配置字段
```

例如：

```text
产品名称 → post_title
尺寸 → product_dimensions
材质 → product_material
颜色 → product_color
```

理论上支持任何 CPT。

## 优点

- 通用性最高
- 可适配各种 WordPress 网站
- 不绑定 WEM
- 可支持 ACF / Meta Box / WooCommerce

## 缺点

开发复杂度会快速增加。

需要考虑：

- Meta Key
- Field Type
- Array
- Serialized Data
- Repeater
- Relationship
- Media
- Taxonomy
- Nested Fields

后台也会越来越像：

> Field Mapping Builder

对普通中小企业管理员不友好。

## 评价

长期可能需要。

但：

> **v0.3.0 不应该一次做满。**

### 当前倾向

**长期方向，暂不作为第一版实现。**

---

# 九、方案 D：Preset Adapter + Generic Adapter + Manual Knowledge

这是当前最倾向的方案。

核心：

```text
Knowledge Source
│
├── Generic WordPress Adapter
├── WEM Adapter
├── WooCommerce Adapter（未来）
├── ACF Adapter（未来）
└── Manual Knowledge Adapter
```

第一阶段先保证：

```text
Generic WordPress Adapter
+
Manual Knowledge
```

然后：

```text
WEM Adapter
```

作为第一个结构化扩展。

# 十、Generic WordPress Adapter

WordPress 插件自动发现可用：

```text
Post Type
```

例如：

```text
post
page
product
solution
faq
download
```

管理员看到的不是技术字段，而是：

# AI 知识来源

例如：

| 内容类型 | 是否启用 |
|---|---|
| Product | ✅ |
| Solution | ✅ |
| FAQ | ✅ |
| Page | ☐ |
| Post | ☐ |
| Download | ☐ |

普通管理员只需要：

> 选择哪些内容 AI 可以读取。

---

# 十一、Generic Adapter 默认读取什么

默认只读取安全字段：

```text
post_title
post_excerpt
post_content
taxonomy
permalink
```

例如：

```text
Product
↓
Title
Excerpt
Content
Category
URL
```

这使得：

> 没有结构化字段的网站也可以使用 AI Knowledge。

---

# 十二、结构化字段作为 Progressive Enhancement

如果网站存在更好的结构化数据：

```text
Model
Dimensions
Material
Length
Color
```

则通过专用 Adapter 加强。

例如：

```text
Generic Product
↓
Title
Content

WEM Product
↓
Title
Content
Model
Dimensions
Material
Length
Color
```

也就是说：

> 普通网站可以用，结构化网站效果更好。

---

# 十三、字段白名单原则

不能：

```text
get_post_meta()
↓
全部进入 AI
```

应该分成：

## 默认安全字段

```text
Title
Excerpt
Content
Taxonomy
URL
```

## 扩展结构化字段

由 Adapter 明确声明：

```text
Dimensions
Material
Length
Color
Model
...
```

其他 Meta：

> 默认忽略。

---

# 十四、真正需要新建的内容类型

目前认为：

> 不应该建立 AI Product / AI Solution / AI FAQ。

真正有必要新建的只有一个：

# AI 补充知识

内部 CPT 可以考虑：

```text
wpaic_knowledge
```

它只用于保存：

> 网站原有内容体系没有，但 AI 客服需要知道的知识。

---

# 十五、AI 补充知识的使用场景

例如：

## 样品政策

```text
样品可以提供。

具体费用及运费根据产品和目的国家确认。
```

---

## MOQ

```text
不同产品 MOQ 不同。

如果产品知识中没有明确 MOQ，
AI 不应该自行给出数字。
```

---

## 报价流程

```text
报价通常需要：

- 产品型号
- 数量
- 颜色
- 目的国家
- 港口
```

---

## 经销商政策

```text
客户咨询区域代理时，需要收集：

- 国家
- 公司名称
- 公司网站
- 预计采购量
```

---

# 十六、AI 补充知识的数据结构

第一版保持简单：

```text
Title
Content
Category
Status
```

不做复杂 Field Builder。

---

# 十七、为什么不强制 Question / Answer

FAQ 适合：

```text
Question
Answer
```

但 Manual Knowledge 不一定是问题。

例如：

```text
报价要求
区域代理政策
样品政策
质保说明
销售流程
```

更适合：

```text
Title
+
Content
```

因此 AI 补充知识不强制采用 Q&A 数据模型。

---

# 十八、FAQ 如何处理

已有 FAQ：

```text
Question
Answer
```

不应该重新复制进：

```text
AI 补充知识
```

而应该：

```text
FAQ Adapter
↓
Knowledge Source
```

FAQ 可以在未来 Retrieval 中拥有较高权重。

---

# 十九、Content Type 与 Knowledge Type 分离

这是当前认为很重要的一点。

例如：

```text
post_type = product
```

AI Knowledge：

```text
knowledge_type = product
```

但：

```text
post_type = page
```

其中某个 Page 可能实际属于：

```text
knowledge_type = company
```

因此不要让：

> WordPress Post Type

完全绑定：

> AI Knowledge Type。

---

概念示例：

object_id
knowledge_type

title
url

content

status

# 三十六、当前推荐方案

一句话：

> **业务数据继续留在原来的 WordPress 内容类型中；AI 插件只负责定义哪些内容可以成为知识，以及如何读取它们。**

也就是：

```text
网站负责：
业务内容

Adapter负责：
把业务内容转换成统一 Knowledge Source

AI Knowledge负责：
使用这些 Source

DeepSeek负责：
根据允许的知识生成自然回答
```

# 当前结论（尚未定稿）

目前 WP AI Chat Lab 的内部倾向是：

> **采用 Generic Adapter + Structured Adapter + Manual Knowledge 的组合方式。**

其中：

```text
Generic Adapter
→ 保证普通 WordPress 网站可以使用

Structured Adapter
→ 提升 WooCommerce / WEM / ACF 等结构化网站的知识质量

Manual Knowledge
→ 补充网站原有内容无法表达的客服与业务规则
```

v0.3.0 暂时只建立：

# Knowledge Source Foundation

而不提前进入：

```text
Chunk
Retrieval
RAG
Grounding
AI Chat
```

这份结论仍等待 Grok、DeepSeek、Gemini 等独立评审后再做最终决定。
